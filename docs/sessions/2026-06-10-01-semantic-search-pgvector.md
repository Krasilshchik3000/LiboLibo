# 2026-06-10 — Сессия 01: семантический поиск переезжает на pgvector

## Контекст

Ветка `feat/semantic-search` уже умела семантический поиск
(`POST /v1/search/semantic`): эмбеддинги через локальную модель
multilingual-e5-small (Transformers.js), ранжирование косинусной близостью.
Но индекс жил в памяти процесса, и это давало три проблемы:

1. **Холодный старт** — первый запрос после деплоя прогревал эмбеддинги
   всего корпуса (~2753 эпизода) прямо в обработчике: минуты ожидания.
2. **Двойной скан** — каждый запрос тянул из БД все эпизоды, чтобы
   проверить, не появились ли новые.
3. **Эфемерность** — рестарт/редеплой терял индекс целиком.

## Что сделали

Перенесли хранение векторов в Postgres (расширение pgvector), а расчёт —
в cron-refresh. План правок: `pgvector-migration.md` (внешний документ),
применён по шагам с двумя исправлениями (см. ниже).

- `episodes.embedding vector(384)` + `embedding_text` (текст, по которому
  посчитан вектор — детект устаревших эмбеддингов при правке эпизода).
- `lib/embedEpisodes.ts` — идемпотентная дозапись векторов, вызывается в
  конце `refreshAllFeeds`. Ошибка шага не валит refresh.
- `routes/search.ts` — эмбеддинг запроса + один SQL-запрос с `<=>`
  (косинусная дистанция), ранжирует Postgres. `/status` считает COUNT по БД.
- `server.ts` — фоновый прогрев модели при старте: первый поиск после
  деплоя не ждёт скачивания модели (110 МБ).
- Удалены: in-memory индекс из `semanticSearch.ts`, `semanticRank.ts`
  и его тест (ранжирует SQL, утилита мертва в рантайме).

### Исправления к исходному плану

1. План предлагал bash-herestring (`<<<`) в `preDeployCommand` —
   Railway выполняет команды через `sh`, заменили на `echo ... |`.
2. Локальный `docker-compose` использовал `postgres:16-alpine` — в этом
   образе нет бинарей pgvector. Сменили на `pgvector/pgvector:pg16`;
   `CREATE EXTENSION` выполняется автоматически перед `prisma db push`.

### Решения

- Premium-эпизоды индексируются и показываются в выдаче наравне с
  обычными (тизер для бесплатных пользователей); `audio_url` гейтится
  через `episodeToDTO` как во всём API. Фильтр — одна строка
  `AND is_premium = false`, если продукт передумает.
- HNSW-индекс не создаём: на ~2753 строках полный перебор — единицы
  миллисекунд. Команда для будущего роста корпуса задокументирована
  в плане (raw `CREATE INDEX ... USING hnsw`).

## Проверено

- `npm run build` (tsc strict) — чисто.
- `npm test` — 47 тестов в 10 файлах, зелёные.
- Локально через Docker (`pgvector/pgvector:pg16`, чистый volume):
  - `CREATE EXTENSION` + `prisma db push` — командами из railway.json, ок;
  - индексация 5 smoke-эпизодов, повторный прогон `embedded=0`
    (идемпотентность: SQL-детект совпадает с `episodeEmbeddingText`);
  - `/status` → `{"indexed": 5}`;
  - «как пережить расставание» находит «Когда отношения заканчиваются»
    первым — ни одного общего слова с запросом.

### Тюнинг порога по замеру

e5 сжимает score в узкую полосу: релевантные пары — 0.86–0.88,
нерелевантные — 0.78–0.81. Исходный дефолт `SEMANTIC_MIN_SCORE=0.75`
не отсекал ничего (рецепты попадали в выдачу про расставание). Дефолт
поднят до **0.84** — по зазору. После этого: точные запросы возвращают
только свой эпизод, бессмысленный («квантовая физика для собак») — пусто.
На реальном корпусе порог стоит перепроверить через env.

## Открытые вопросы

- Смена образа Postgres локально: существующий volume `pgdata`,
  инициализированный alpine-образом, может потребовать
  `docker compose down -v` (пересоздание с сидом).
- Поддерживает ли Railway-плагин Postgres расширение vector — если нет,
  preDeploy упадёт громко на `CREATE EXTENSION`; нужно проверить при
  первом деплое.
